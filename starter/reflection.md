I made a key design decision early in the project to build the agent around a modular, tool-based workflow rather than hard-coding logic into a single script. This meant separating responsibilities such as fetching catalog data, processing refunds, and tracking orders so each function had a clear purpose and could be tested independently. I chose this structure because it made the system easier to reason about, easier to debug, and more adaptable if the project needed new capabilities later. It also aligned with the idea of an agent that can interact with external systems while still remaining maintainable for future updates.

One concrete challenge I encountered was that the browser tool was not working as expected. At first, I assumed the issue was with the page or the logic behind the automation, but after tracing the failure I realized the tool lacked the necessary permissions to access the browser environment properly. This prevented it from opening pages and interacting with the web, which blocked the workflow. I resolved it by identifying the missing access requirements and adding the necessary permissions in the environment configuration. Once the permissions were in place, I validated the browser tool with a small test to confirm it could load and interact with the target resource correctly.

If I were to extend this agent for a production environment, I would focus on reliability, observability, and security. I would add structured logging around each tool call, enforce permission-based access controls, and include retry logic and failure handling for external services. I would also introduce monitoring for latency, errors, and tool usage so the system can detect issues before they affect users. In production, the agent should not only complete tasks, but also fail gracefully and provide clear diagnostics when something unexpected happens.
